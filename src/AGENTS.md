# 워크스페이스 운영 규칙

## 폴더별 역할과 소유권

- `../skills/`: MCP에 접속하는 에이전트가 로컬에서 먼저 읽는 클라이언트 스킬을 소유한다. 서버의 Skill 등록 데이터가 아니다.
- `skills/`: 관리 웹과 MCP 서버가 제공하는 Skill 등록 데이터를 소유한다. 부트스트랩 스킬을 이곳에 두지 않는다.
- `builtin-skills/`: 서버 시작 시 최초 등록할 내장 Skill 원본을 소유한다. 기존 등록 데이터를 덮어쓰지 않는다.
- `lib/`: MCP 도구·리소스 및 Skill 저장소 구현을 소유한다. 클라이언트 스킬 작업에서는 인터페이스 확인을 위해 읽기만 한다.
- `public/`: 관리 웹 화면의 렌더링·상호작용·표시 스타일을 소유한다.
- `README.md`: 실행·연결 안내를 소유한다. 클라이언트 스킬 작업에서는 연결 정보 확인을 위해 읽는다.

## 기본 클라이언트 스킬 제작 워크플로

- 정확한 실행 트리거: `이 mcp를 사용하기 위한 기본 skill를 만들어줘`.
- 순서: `project_design/request.md`, `src/lib/mcp.ts`, `src/README.md`의 존재와 내용을 먼저 확인한다. 세 파일의 설명과 실제 도구 계약을 대조하고 `../skills/skillport-client/SKILL.md`를 작성한다. 마지막에 스킬 구조와 UTF-8 인코딩을 검증한다.
- MCP 도구는 위 소스 확인이 끝나기 전에는 호출하지 않는다. 이 워크플로에 MCP 쓰기가 필요해지면 서버별 필수 매개변수의 존재·형식·대상 ID 일관성을 먼저 검증한다.
- 중지 조건: 소스 파일을 읽을 수 없거나, 도구 계약이 서로 충돌하거나, 대상 경로가 하나로 확정되지 않거나, 요청 범위 밖 수정이 필요한 경우다. 사용자에게 차단 사유·요청된 결정·영향을 알려 확인을 기다린다.
- 오류 처리: 실패 시 원인·증거·다음 조치와 재실행 조건을 보고한다. MCP 쓰기가 있었다면 대상 ID·실행 결과·실패 사유·재실행 필요성도 보고한다.
- 재실행 조건: 사용자가 다시 요청하거나 소스 계약이 변경되었을 때만 기존 파일을 갱신한다. 동일 내용이 있으면 중복 파일이나 두 번째 등록을 만들지 않는다.

## 내장 `usage` Skill 등록 워크플로

- 정확한 실행 트리거: `mcp에 usage로 만들어주고... 웹에서 등록된 데이터들은 어디에 보관되는거지?`.
- 순서: `src/lib/registry.ts`, `src/server.ts`, `src/docker-compose.yml`을 확인한다. 저장 형식을 확인한 뒤 `builtin-skills/usage/` 원본을 작성하고 서버 시작 시 이름 `usage`가 없을 때만 등록되도록 연결한다. 기존 데이터를 읽고 테스트 및 UTF-8 검증을 수행한다.
- 중지 조건: 기존 `usage`의 소유권이나 저장 경로를 확정할 수 없거나 등록 과정이 기존 버전을 덮어쓰게 될 때다. 이 경우 차단 사유·요청된 결정·영향을 보고한다.
- 오류 처리: 등록 또는 검증 실패 시 원인·증거·다음 조치와 재실행 조건을 보고한다.
- 재실행 조건: 서버 재시작 후 `usage`가 없을 때만 다시 시도한다. 이미 등록된 경우 중복 생성하지 않는다.

## Skill 목록 상태 선택 워크플로

- 정확한 실행 트리거: `그리드 메뉴에 상태 누르고 셀렉트 버튼으로 해주던가..`.
- 순서: `public/app.js`의 목록 렌더링과 상태 변경 요청을 확인하고, `server.ts`의 상태 API 계약을 대조한다. `public/`의 상태 조작 UI를 수정한 뒤 구문·인코딩을 검증한다.
- 중지 조건: 상태 값 또는 API 계약이 불명확하거나, 목록 변경에 무관한 저장 데이터를 수정해야 할 때다. 차단 사유·요청된 결정·영향을 보고한다.
- 오류 처리: 요청 실패 시 선택 값을 이전 상태로 되돌리고 사용자에게 오류를 표시한다. 검증 실패 시 원인·증거·다음 조치와 재실행 조건을 보고한다.
- 재실행 조건: 사용자가 다시 요청하거나 목록 구현이 변경되었을 때만 다시 적용한다. 동일한 이벤트 핸들러를 중복 등록하지 않는다.

## Skill 편집 화면 워크플로

- 정확한 실행 트리거: `편집하는 화면도 만들어줘`.
- 순서: `public/app.js`의 상세·목록 UI와 `server.ts`의 PUT API, `lib/registry.ts`의 버전 제약을 확인한다. `public/`에 편집 UI를 만들고 새 버전으로 저장하도록 연결한다. 구문·인코딩과 입력 검증을 확인한다.
- 중지 조건: 편집 대상 이름을 확정할 수 없거나 기존 버전 덮어쓰기가 필요한 경우다. 차단 사유·요청된 결정·영향을 보고한다.
- 오류 처리: 저장 실패 시 편집 내용을 유지하고 오류를 화면에 표시한다. 검증 실패 시 원인·증거·다음 조치와 재실행 조건을 보고한다.
- 재실행 조건: 사용자 재요청 또는 편집 API 계약 변경 시에만 다시 적용한다. 저장 중에는 버튼을 비활성화해 중복 버전 생성 요청을 막는다.

## URL 원본 업데이트 확인 워크플로

- 정확한 실행 트리거: `자동 갱신하지 말고... 목록 같은데에 업데이트가 있는지 비교해주고.. 있으면 업뎃을 누르면 갱신되는 방식으로.. 가장 마이너 버젼은 올라가고 이런식으로 가능해?`.
- 순서: `server.ts`의 URL 가져오기, `lib/registry.ts`의 메타데이터·버전 저장, `public/app.js`의 목록을 확인한다. 원본 주소와 기준 해시를 저장하고, 목록 첫 조회·재확인 시 비교하는 API 및 목록 버튼을 만든다. 업데이트 버튼을 누른 경우에만 PATCH 번호를 올려 새 버전으로 저장한다. 테스트와 인코딩을 검증한다.
- 중지 조건: 원본 URL이 없거나 허용되지 않는 URL이거나, 다른 이름의 Skill을 가리키거나, 새 버전 저장이 기존 버전을 덮어쓸 위험이 있을 때다. 차단 사유·요청된 결정·영향을 보고한다.
- 오류 처리: 확인 또는 업데이트 실패 시 저장된 Skill을 유지하고 사용자에게 오류를 표시한다. 검증 실패 시 원인·증거·다음 조치와 재실행 조건을 보고한다.
- 재실행 조건: 목록에서 아직 확인하지 않은 Skill을 보거나 사용자가 재확인·업데이트를 요청할 때만 원본을 가져온다. 자동 주기 동기화는 하지 않고, 동시 업데이트 요청은 중복 저장되지 않게 막는다.
